## 一、巡检明细:判定阈值总表(规则引擎直接采用)

> 原则(头部共性):每项必有阈值+依据+建议;阈值集中放规则 YAML,允许用户改。

| 检查项 | 判定标准(FAIL 线) | 依据 |
|---|---|---|
| CPU 利用率 | 5s >80% warning;>95% critical | 华为/思科通用实践 |
| 内存利用率 | >80% warning;>90% critical;最大可用块<总内存 10% 加警示 | 同上 |
| Flash/存储 | >80% warning(日志盘满可致宕机) | S5700 实战清单 |
| 温度 | 状态非 Normal,或超厂商门限(如 >65℃ warning) | `display device temperature` |
| 电源 | 任一 Fail/Absent(**在线冗余数<2 时升级 critical**) | eSight 部件监控 |
| 风扇 | 任一 Fail/转速 0 | 同上 |
| 光模块 DDM | Rx 功率低于厂商 Rx_low 门限(链路衰减先兆);Tx/Rx 超告警区间;偏置电流异常。通用参考:单模 10G Rx 范围约 -1~-12 dBm(以厂商 SFF-8472 门限回显为准,**有 DDM 门限回显优先用回显值**) | Cisco DOM / SFF-8472 |
| 接口错包 | CRC/输入/输出错误**增量>0**(对比上期) | SolarWinds 接口监控 |
| 接口状态 | 管理 Up 且链路 Down(预期停用白名单豁免) | 既有规则 |
| OSPF/BGP 邻居 | 任一邻居非 FULL/Established | Juniper/Cisco 验证指南 |
| ARP/MAC 表 | 规模>容量 80% | 头部容量告警惯例 |
| 未保存配置 | running ≠ startup → **critical**(重启即丢) | SolarWinds NCM |
| 上次重启原因 | 异常重启(非 power-on/normal)→ warning | 运维实践 |

**每厂商新增命令映射(首批华为/H3C,约 20 条)**:温度 `display device temperature`、光模块 `display transceiver detail`(H3C `display transceiver diagnosis`)+ 华为 `display transceiver diagnosis`、邻居 `display ospf peer`/`display bgp peer`、ARP/MAC 规模 `display arp all`/`display mac-address total`、存储 `dir`、配置一致性 `compare configuration`、NTP `display ntp-service status`、syslog 外发 `display current-configuration | include syslog`、License `display license`。Cisco/Juniper 对应 show/junos 命令同表入库。

## 二、等保 2.0 基线包(第二规则包,与"基础健康包"并列)

查证依据:等保 2.0 基本要求 + 华为/H3C 加固实战。**每个基线包 = 一个可勾选 YAML,报告输出"合规达标率"**。

| 基线项 | 采集来源 | 判定(FAIL 线) |
|---|---|---|
| 登录失败锁定 | 配置解析(password-control/AAA 安全策略) | 未配置锁定(常见 5 次锁 15 分钟) |
| 口令策略 | 配置解析(最短长度/复杂度/有效期) | 未配置或弱于默认(长度<8/无复杂度) |
| 远程管理协议 | VTY/服务配置 | Telnet 开启;SSH 非 v2 |
| 管理访问控制 | VTY ACL | 未配置管理源限制 |
| SNMP | 配置解析 | 默认团体字 public/private;未限源;建议 v3(信息级) |
| NTP 同步 | `display ntp-service status` | 未同步/仅单服务器(双源为佳) |
| 日志外发留存 | 配置解析 loghost | 未配置远程 syslog(等保留存≥6 个月) |
| 空闲超时 | VTY idle-timeout | 未配置或>10 分钟 |

规则文件组织:`config/rules/baseline_basic.yaml`(基础健康)、`baseline_dengbao.yaml`(等保)、既有厂商专项包——报告按"包×达标率"呈现(如 基础 95% / 等保 62%,并列整改清单)。

## 三、登录方式深化(Telnet P0 / Console P2)

### 3.1 Telnet(查证:netmiko 4.x 内置 62 种 `_telnet` 类型)

| 现有 SSH 类型 | Telnet 类型(自动映射) |
|---|---|
| hp_comware(H3C/华三) | `hp_comware_telnet` |
| huawei | `huawei_telnet` |
| cisco_ios | `cisco_ios_telnet` |
| ruijie_os | `ruijie_os_telnet` |

实现要点:驱动表加 `netmiko_telnet_device_type` 属性;设备档案 `login_method=telnet` 时端口默认 23、连接参数换 telnet 类型;凭据/super 逻辑复用。**注意锁定 netmiko ≥4.x(3.3.0 有 telnet 回归 bug,issue #1945)。**

### 3.2 Console(两种形态,P2)

1. **本机串口**:netmiko serial 类型(`cisco_ios_serial` 等)+ `serial_settings={'port':'COM3','baudrate':9600}`,底层 pyserial;设备档案 login_method=console + 串口参数(COM 口/波特率 9600-115200-8N1)。
2. **反向 Telnet(带外推荐)**:通过机房 Console 服务器(思科 2509/Opswise 等)的 `IP:端口` 反向 telnet 到设备串口——复用 Telnet 通道,只需设备档案 host=console服务器IP、port=线路端口。这是运维带外管理标准打法,优先支持此形态。

### 3.3 登录路由矩阵(一次巡检混合通道)

设备档案 login_method ∈ {ssh, telnet, web, api, console} → 巡检器按设备各自路由;公司级报告"巡检概述"章节统计各通道设备数。

## 四、全网健康评分模型(借鉴 Cisco Catalyst Center 加权 + Optigo 关键项否决)

**设备健康分(0~100) = Σ(类别得分 × 权重),关键项一票否决降档:**

| 类别 | 权重 | 得分规则 |
|---|---|---|
| 硬件环境(电源/风扇/温度/光模块/单板) | 30% | 该类检查项 PASS 占比 |
| 资源(CPU/内存/存储) | 20% | 同上 |
| 链路接口(状态/错包) | 20% | 同上 |
| 安全合规(基线包达标率) | 15% | 达标项占比 |
| 日志告警/配置管理 | 15% | 同上 |

**一票否决**:任一 critical 级 FAIL(电源失效/未保存配置/温度 critical)→ 总分强制 ≤40 并标红(借鉴 Optigo "critical checks" 机制)。
**分级**:≥90 优 / 75~89 良 / 60~74 关注 / <60 差。
**全网分** = 各设备分算术平均(按客户分组时给分组分);报告封面与"总体健康度"章节直接使用,并与上期分数对比(↑↓)。

## 五、报告体系深化(引擎选型 + 字段级规格)

### 5.1 模板引擎选型(查证:docxtpl 为 Word 报告最佳实践)

| 产物 | 引擎 | 理由 |
|---|---|---|
| Word(四套模板) | **docxtpl(python-docx-template)** | 用 Word 本身设计模板+Jinja2 标签({%p %}段落/{%tr %}表格行),**乙方用户可自行改封面样式/换 Logo/调字体而不动代码**;比纯 python-docx 拼装可维护性强 |
| PDF | 既有 Word→PDF 转换链(本机 Word/LibreOffice) | 已有能力复用 |
| Excel(C 模板) | **openpyxl**(预置样式模板 xlsx) | 样式模板与数据分离 |
| HTML/在线预览 | 既有 Jinja2 报告 | 已有 |

模板文件放 `config/report_templates/`,缺失时回退内置默认——**模板即配置**。

### 5.2 四套模板字段级规格

**A 正式汇报版(Word,5~8 页)**
- 封面:报告编号 `XJ-{客户代码}-{YYYYMM}-{序号}`、甲方名称+Logo 位、乙方名称、合同编号、巡检周期、报告日期、密级标注
- 一、巡检概述:客户名/设备数/巡检方式分布(SSH×n/Telnet×n/Web×n)/巡检人/起止时间
- 二、总体健康度:全网评分+分级色块、与上期对比箭头、PASS/FAIL/UNKNOWN 分布、基线包达标率两条
- 三、TOP 风险与整改建议(表:序号/设备/严重级/问题/依据/建议/建议完成期限,按 critical→warning 排序,取前 10)
- 四、上期问题复查(表:上期问题/本期状态[已解决·仍存在·设备下线]/备注)
- 五、设备清单摘要(附表 A 同源精简)
- 签字页:巡检人/审核人/甲方接收人签名+日期栏,甲乙双方盖章区(双框)

**B 工程明细版(Word/HTML)**
= A 全部章节 + 逐设备章节(信息头[归属客户/型号/版本/uptime/评分] + 九大类结果表[检查项/结果/实测值/阈值/建议] + 原始回显折叠块[每命令一块,等宽字体])

**C 台账表格版(Excel,3 Sheet)**
- Sheet1 设备台账:客户/名称/IP/厂商/型号/序列号/软件版本/上线位置/负责人/健康分
- Sheet2 检查结果矩阵:设备×检查项的 PASS/FAIL/UNKNOWN 着色矩阵(条件格式)
- Sheet3 异常跟踪:问题/设备/严重级/首次发现期次/连续期次/责任方/状态/复测结果

**D 变更对比版**
- 上期 vs 本期:配置 diff(unified 格式,增行绿/删行红)+ 接口错包增量表 + 新增告警清单 + 新增/下线设备清单

### 5.3 上期复查闭环(启用既有 history 库)

history 表最小结构:`run_id/巡检时间/客户/设备/检查项/状态/严重级/消息/报告文件`;复查逻辑=取同(客户,设备,检查项)上期 FAIL → 比对本期状态。异常跟踪 Sheet 的"连续期次"即从此库统计(连续 3 期未解决自动升级严重级展示)。

### 5.4 归档与编号规范

`output/{客户名}/{YYYY-MM}/XJ-客户代码-YYYYMM-序号_模板标识.{docx|xlsx|pdf}`;报告编号全局递增,history 库存根。

## 六、定时巡检与邮件分发(P2)

- **调度**:不自研调度器,采用 **Windows 任务计划程序**调用 CLI(单机离线最稳,断电不丢任务);工具"设置"面板提供"安装/卸载巡检计划"按钮(schtasks 封装,周期:每周三 02:00 / 每月 1 日 02:00 可选)。
- **分发**:设置面板配 SMTP(服务器/端口/SSL/账号授权码/发件人/甲方收件人/乙方收件人);巡检完成后正式版→甲方、A+B+C→乙方,附件按归档命名;失败重试 1 次并状态栏告警。凭据存本机配置,不入报告。

## 七、实施任务分解(半天粒度,含验收标准)

| # | 任务 | 量 | 验收标准 |
|---|---|---|---|
| P0-1 | Telnet 通道:驱动 telnet 类型映射+档案路由+端口联动 | 1d | telnet 设备真机/模拟登录采集全通;类型合法性测试过 |
| P0-2 | 九大类明细·华为/H3C 批次(温度/光模块/邻居/ARP/存储/一致性/重启原因) | 2d | 每新项:fixture 解析测试过+规则阈值入 YAML+报告呈现 |
| P0-3 | 健康评分模型(设备分/全网分/否决制) | 0.5d | 评分单元测试:满分/否决/分级边界;报告封面出分 |
| P0-4 | docxtpl 模板引擎接入+模板 A(封面/签字页模板化) | 1.5d | 用户改模板 Logo/字体后重新生成生效 |
| P0-5 | 模板 B 字段级章节+模板 C Excel 三 Sheet | 1.5d | 示例数据三产物齐全,列与规格一致 |
| P1-1 | history 库接入+上期复查+异常跟踪统计 | 1d | 连跑两期,复查表与"连续期次"正确 |
| P1-2 | 配置快照留存+diff+模板 D | 1.5d | 两期配置差异正确高亮 |
| P1-3 | 等保基线包(8 项)+达标率呈现 | 1d | 基线项判定有配置依据;报告出双包达标率 |
| P2-1 | 反向 Telnet 带外+本机串口 console | 1.5d | console 通道采集演示 |
| P2-2 | 计划任务(schtasks 封装)+SMTP 分发 | 1.5d | 自动触发→报告生成→双发邮件收到附件 |

总计:P0 6.5d / P1 3.5d / P2 3d。每任务完成即回归全量测试+绿色包重建。
